# Presentation Contract

> **قرارداد مشترک**
>
> این سند تعیین می‌کند خروجی‌های این پروژه **چطور ارائه شوند**، نه اینکه چه بگویند.
>
> محتوا مال Skill است. ارائه مال این سند.

## چرا وجود دارد

یک بازرسی می‌تواند تحلیل درستی داشته باشد و باز هم بی‌فایده باشد، چون خواننده نمی‌تواند
آن را بخواند.

در اولین ارزیابی `security-review` دقیقاً همین رخ داد: تحلیل امنیتی قوی بود، ولی گزارش
دیوارِ متن شد و قرارداد خروجی رعایت نشد.

از این پس کیفیت ارائه بخشی از Evaluation رسمی است، نه یک سلیقهٔ ظاهری.

## دامنه

روی همهٔ خروجی‌های انسانی و اسناد ساختاری پروژه اعمال می‌شود: Project Map، خلاصهٔ
امنیتی، خلاصهٔ Reviewerهای آینده، Remediation Plan، نتیجهٔ Verification، پیام‌های
وضعیت، `README`، `BLUEPRINT`، اسناد design، و توضیح‌های رو به کاربر.

سند JSON از نظر ساختار تابع `findings-schema.md` است، ولی متن‌های داخلش هم مشمول
بخش [متن داخل artifact](#متن-داخل-artifact) هستند.

این سند از این لحظه authoritative است. اسناد قدیمی فقط وقتی هماهنگ می‌شوند که به
دلیل دیگری ویرایش شوند — بازنویسی انبوه لازم نیست و خواسته نشده.

## اصل اصلی

هر خروجی باید در چند ثانیه قابل اسکن باشد:

```text
Clean · Scannable · Consistent · Compact · Professional
```

آزمون ساده: خواننده باید بدون خواندن کامل، بفهمد سند چند بخش دارد و کجا باید نگاه کند.

## ساختار

سلسله‌مراتب ساده بماند: عنوان سند، بخش اصلی، و در صورت نیاز واقعی زیربخش.

بیش از سه سطح heading استفاده نشود مگر ضرورت واقعی باشد. برای دو جمله heading ساخته
نمی‌شود.

## پاراگراف

پاراگراف کوتاه باشد — ترجیحاً دو تا چهار خط — و یک ایدهٔ اصلی داشته باشد.

پاراگراف طولانی به چند پاراگراف کوتاه شکسته می‌شود، نه اینکه فشرده‌تر نوشته شود.

## فهرست‌ها

برای مجموعهٔ موارد از bullet استفاده کن. حداکثر یک سطح تودرتویی، مگر واقعاً لازم باشد.

فهرست جای جمله‌های کوتاه است، نه جای پاراگراف.

## فضای خالی

بین بخش‌های مستقل فضای خالی بگذار. اطلاعات به هم چسبیده، خوانده نمی‌شود.

فضای خالیِ خوانا بخشی از کیفیت خروجی است، نه اتلاف جا.

## تأکید و کد

`bold` فقط برای چیزی که واقعاً مهم است. وقتی همه‌چیز bold باشد، هیچ‌چیز bold نیست.

backtick فقط برای این موارد: نام فایل، symbol، تابع، route، فیلد، دستور، و مقدار
literal.

code block فقط برای کد، JSON، دستور shell، schema، یا یک نمودار جریانِ کوچک.

متن عادی داخل code block گذاشته نمی‌شود. code block کادر تزئینی نیست.

## جدول

جدول فقط وقتی که مقایسه یا ماتریس واقعاً با جدول خواناتر می‌شود:

| Finding | Severity | Confidence | Status |
|---|---|---|---|

توضیح طولانی داخل جدول ریخته نمی‌شود.

## زبان

متن رو به کاربر فارسی است.

اصطلاح فنی‌ای که ترجمه‌اش دقت را کم می‌کند به انگلیسی می‌ماند — مثل authentication،
authorization، middleware، finding، repository، Project Map.

نام فایل و symbol و route و کد همیشه با backtick می‌آید. ترکیب بی‌قاعدهٔ فارسی و
انگلیسی پذیرفته نیست.

## خلاصهٔ کاربر

هر Reviewer یک خلاصهٔ ساده می‌دهد. خلاصه گزارش کامل را بازنویسی نمی‌کند — artifact
جزئیات را نگه می‌دارد و خلاصه فقط برای تصمیم سریع کاربر است.

شکل مرجع:

```markdown
## نتیجه

۴ Finding پیدا شد:

- High: 1
- Medium: 3

### مهم‌ترین مورد

`SEC-001` — <عنوان کوتاه finding>

Severity: High
Confidence: Inferred
Location: `<file>:<line>`

یک یا دو جملهٔ توضیح.

### پوشش

بررسی شد:
- Authentication
- Authorization
- Business logic

بررسی نشد:
- Production firewall
- Real environment configuration
```

بیشتر از این نه.

## متن داخل artifact

سند ماشین‌خوان source of truth است، ولی متن‌های داخلش هم باید کوتاه باشند:

- `title` — یک جملهٔ کوتاه
- `explanation` — فقط آنچه برای فهم مشکل لازم است
- `impact` — اثر واقعی
- `verification` — روش مشخص اثبات یا رد
- `suggested_fix` — کوچک‌ترین جهت اصلاح

داخل فیلدهای JSON مقاله نوشته نمی‌شود.

## وضعیت workflow

وضعیت باید کوتاه و صریح باشد و لای چند پاراگراف گم نشود:

```text
PASS      دلیل کوتاه · unknownهای باقی‌مانده
OPEN      چه چیزی باز است · مرحلهٔ بعد
BLOCKED   چه چیزی کم است · برای ادامه چه لازم است
```

## Remediation — تصمیم ثبت‌شده برای آینده

`remediation-planner` هنوز ساخته نشده. وقتی ساخته شود، هر مورد اصلاح باید شکل ثابتی
داشته باشد:

```markdown
## SEC-001 — <title>

Priority: High

### Goal
### Change
### Must remain unchanged
### Verification
```

بدون prose طولانی و بدون قالب‌بندی تصادفی.

## بسته‌های مستقل Skill

یک Skill که به‌صورت مستقل نصب می‌شود به این repository دسترسی ندارد.

پس هر بستهٔ Skill فقط **حداقل قواعد ارائه‌ای** را که در زمان اجرا لازم دارد داخل خودش
می‌آورد. کل این سند کپی نمی‌شود.

این سند source of truth طراحی می‌ماند؛ بستهٔ Skill خلاصهٔ عملیاتی آن را حمل می‌کند.
